Requirement 20, criterion 13: the measured query plan for each new date-range query is

Raw artifacts, captured together:

- `query-plans/stage-2-v1.9.1.txt` — the `explain (analyze, buffers)` output verbatim
- `query-plans/stage-2-v1.9.1.json` — the same capture in machine-comparable form

## What this record is, and what it is not

It is a baseline and an existence proof. It shows the three index shapes the redesign
relies on are present, valid, and able to serve the predicates the read paths will
issue. It fixes the plan each query got on a known date against known row counts, so a
capture taken at real volume has something to be compared against.

It is not a performance result, and nothing in it should be quoted as one. The tables
hold tens to hundreds of rows. At that size Postgres reads the whole table because
reading one heap page genuinely costs less than descending a btree and then visiting the
heap anyway. Four of the six plans below are sequential scans, and that is the planner
being right, not the indexes failing. Any speed-up claim would need volume this database
does not yet have.

The forced-index plans in the capture are labelled `DIAGNOSTIC`. They were produced with
`enable_seqscan = off`, which is not a setting any application query runs under. Their
only job is to answer one question — can this index serve this predicate at all — and
their costs and timings carry no other meaning.

## What the planner actually did

| Query | Window | Chose | Index usable when forced |
| --- | --- | --- | --- |
| clock entries, all employees | 1 date | Seq Scan + Sort | not tested (same shape as below) |
| clock entries, all employees | 31 dates | Seq Scan + Sort | yes, `idx_time_clock_clock_in` |
| schedules, all employees | 1 date | Bitmap Index Scan on `idx_employee_schedules_date` + Sort | n/a, already chosen |
| schedules, all employees | 31 dates | Index Scan on `idx_employee_schedules_date`, no sort | n/a, already chosen |
| time-off overlap, all statuses | 31 dates | Seq Scan + Sort | yes, `idx_pto_requests_range` |
| time-off overlap, approved only | 31 dates | Seq Scan + Sort | yes, `idx_pto_requests_approved_range` |

Reading across the three patterns:

**Clock entries.** Sequential scan, one shared buffer hit, 47 rows returned. The two
windows produced identical plans and identical row counts because every clock row in the
database falls inside both — an artifact of holding two days of data, not a property of
the query. `idx_time_clock_clock_in` serves the predicate when forced, at cost 0.14..4.02
against the sequential scan's 0.00..1.58, which is exactly why it was not chosen. Worth
noting separately: the index already shows 147 scans since the statistics reset. It is not
sitting idle waiting for the redesign — `/api/payroll/calculate` and
`/api/time-clock/reports` already range over `clock_in` across all employees, and those
are the queries reaching it.

**Schedules.** The only pattern where the index wins on merit today, at 924 rows.
`idx_employee_schedules_date` is `(schedule_date, profile_id)` and the query orders by
`schedule_date, profile_id`, so the 31-date plan is a plain index scan with no sort node
at all — the index supplies the order. The single-date plan uses a bitmap index scan and
then sorts, since a bitmap loses index order. This index predates the migration
(v1.2.0), which is why v1.9.1 adds nothing for Requirement 20, criterion 11.
One reading note on the 31-date plan: 509 buffer hits for 524 rows is close to one heap
visit per row, because the rows sit in the heap roughly in `profile_id, schedule_date`
insertion order while the index walks `schedule_date` order. Low correlation like that is
what eventually pushes a planner off an index scan as a table grows, so it is the number
to watch in the next capture rather than the timings.

**Time-off.** Sequential scan over 3 rows. Both new indexes are reachable when forced.
Two caveats on this table specifically:

- `pto_requests` has never been analysed, so the planner is working from default
  estimates: it guessed 1 row where 2 matched. The choice is still correct at this size,
  but the estimate carries no information. A capture at real volume should `analyze
  public.pto_requests` first, or the plan will be measuring missing statistics rather
  than the query.
- No row currently has status `approved`, so `idx_pto_requests_approved_range` is an
  empty partial index, 8 KB. The diagnostic confirms the planner will use it and that
  `status = 'approved'` implies its predicate; it cannot confirm anything about its
  selectivity until approved requests exist. The `partially_approved` branch of the
  predicate matches nothing until stage 4 (`v1.9.3`) widens the status check
  constraint — deliberate, and explained in the migration header.

## Release gate

Requirement 20, criterion 13 is satisfied for the three new range queries: each has a
measured plan on record, taken before the query ships, with the row counts and capture
date it was measured against. The indexes named in criteria 10, 11, and 12 are present,
valid, and demonstrably able to serve their queries.

What the capture does not establish, and what the next one needs to: whether the planner
switches to these indexes at production volume, and whether the plans stay stable when
the read paths from task 7 add their joins and filters. Re-capture after task 7.1 lands
the real service queries, and again when clock and time-off volume grows by an order of
magnitude.

## Repeating this capture

Worth automating, and automated. Three reasons: this stage is one of six, and stages 4
and 6 change `pto_requests` statuses and add columns the predicates touch; the value of
the record is entirely in comparing captures, which needs the windows and query text held
constant; and a hand-run `explain` cannot be trusted to have used the same text twice.

`scripts/capture-attendance-query-plans.mjs` holds the six queries, resolves both windows
from a single `--anchor`, records row counts, data extent, and the full index inventory
alongside the plans, and writes the `.txt` and `.json` pair. It is read-only — every
statement is a `select` or an `explain` of a `select` — and it exits non-zero if an index
turns up invalid or cannot serve its query even with `enable_seqscan` off.

```bash
# This capture, reproducible as recorded
node --env-file=.env.local scripts/capture-attendance-query-plans.mjs \
  --label stage-2-v1.9.1 --anchor 2026-07-31 --force

# A later stage, same queries and window offsets, new artifact
node --env-file=.env.local scripts/capture-attendance-query-plans.mjs \
  --label stage-4-v1.9.3 --anchor 2026-07-31
```

Pass the same `--anchor` every time. Left out, it defaults to the database's
`current_date`, which makes the windows move and the captures incomparable.
