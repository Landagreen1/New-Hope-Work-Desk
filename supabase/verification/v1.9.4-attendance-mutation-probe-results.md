## Why a probe was needed

The migration's own verification block reports structure: two functions exist, both are
`security definer`, both pin `search_path`, the policy names `waitlisted`. None of that
is behaviour. A function that compiles is not a manager who was turned away, and an
audit insert written last is not a change that was rolled back when it failed.

The probe runs inside a single transaction that ends in `rollback`, so nothing it
writes is committed. Impersonation is `set local role authenticated` plus `set local
request.jwt.claims`, which is what makes `auth.uid()` inside each function answer as a
specific signed-in user. Fixture instants are in 2099 and the subject profile is chosen
as one with no open clock entry, so no live session is disturbed.

## The stage gate (Requirement 23, criterion 5)

`npm run verify-payroll-parity` before applying: exit 0, no payroll period with status
`processed` or `paid` exists on the project, so parity holds vacuously. There is no
stored payroll figure for a correction to contradict.

### The two that matter most

**A failed audit write rolls the change back.** Requirement 16, criterion 6. The
correction's clock-in, break minutes, and total hours read
`2099-03-02 13:30:00+00|45|6.75` before the call and the same three values after it,
while the function answered `audit_write_failed` and quoted the refusal. The audit
insert being the last statement of the block is what makes that hold: the block is a
subtransaction, so by the time its handler runs, the change is already undone.

**The first reviewer stands.** Requirement 12, criterion 16. Two calls, one review row,
one audit row, and the second call returning the first call's reviewer and timestamp
rather than its own.
